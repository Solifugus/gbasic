# gBASIC Site Auth, Sessions, and CSRF Plan

The current site uses local admin and CSRF token files only as dogfooding
shortcuts. They are acceptable for loopback development and integration tests,
but they are not a public authentication system.

This plan defines the target shape for public deployment and the gBASIC runtime
capabilities needed to implement it cleanly.

## Public Exposure Rule

Until this plan is implemented, nginx should keep `/admin` unreachable from the
public internet and public write routes should be treated as experimental.

The deployment template deliberately returns `404` for `/admin`.

## Target Model

The first production-capable model should be deliberately small:

- one or more admin users stored in Postgres,
- password hashes stored with per-password salts and algorithm metadata,
- login form that creates a server-side session,
- logout route that invalidates the session,
- secure session id stored in an HttpOnly, SameSite cookie,
- CSRF token tied to the server-side session,
- CSRF validation on every state-changing form,
- session expiration and explicit session revocation,
- moderation actions attributed to an authenticated username.

Forum posting can initially remain anonymous or pseudonymous, but public
posting should still have spam controls before launch.

## Database Shape

Expected production tables:

```sql
create table gbasic_site_users (
    id integer generated by default as identity primary key,
    username text not null unique,
    password_hash text not null,
    password_algorithm text not null,
    admin boolean not null default false,
    disabled boolean not null default false,
    created_at timestamp not null default current_timestamp,
    updated_at timestamp not null default current_timestamp
);

create table gbasic_site_sessions (
    id text primary key,
    user_id integer not null references gbasic_site_users(id) on delete cascade,
    csrf_token text not null,
    created_at timestamp not null default current_timestamp,
    expires_at timestamp not null,
    revoked_at timestamp
);
```

The gBASIC site schema now includes these users and sessions tables. The site
does not yet expose login/logout routes or password-based authentication.

The session id and CSRF token must come from cryptographically secure random
bytes, not predictable strings.

## Cookie Requirements

Session cookies should be formatted with:

- `HttpOnly`,
- `Secure` when served over HTTPS,
- `SameSite=Lax` or stricter,
- `Path=/`,
- a bounded max age or expiration.

gBASIC WebServer request and response records now expose explicit cookie
parsing and `Set-Cookie` emission.

## Password Requirements

Password hashing should use a modern password hash such as Argon2id, bcrypt, or
scrypt. Plain SHA-style hashes are not enough for password storage.

The runtime or standard library should expose a safe helper instead of making
applications assemble password hashing by hand.

## CSRF Requirements

CSRF tokens should be generated per session and stored server-side with the
session. Forms include the session token as a hidden field. State-changing
routes verify both:

- the session cookie maps to a live session,
- the submitted CSRF token matches the session.

The current file-backed CSRF token does not protect separate sessions from one
another and must remain development-only.

The site now has a temporary local-token login that creates a server-side
session cookie. It exists to dogfood session plumbing and is not production
password authentication.

## Runtime Gaps

Dogfooding the site points to these remaining runtime or standard-library
needs:

- cryptographically secure token generation is available through
  `secure_token(length)`, but raw random bytes are not exposed,
- password hashing helper,
- cookie parsing and `Set-Cookie` response emission are available in the
  WebServer request/response records,
- redirect response helper is available as `webserver.redirect(...)`,
- session-id-safe tokens are available through `secure_token(length)`,
- time helpers for expiration comparisons,
- standard form decoding and HTML escaping helpers.

## Interim Options

Until the runtime has those pieces, the safest deployment posture is:

- keep `/admin` blocked at nginx,
- keep admin token files local-only,
- do not advertise public posting,
- use the site publicly for read-only pages first,
- treat forum write paths as staging or private-beta functionality.

An interim invite-only posting token could be added, but it should be described
as spam friction, not authentication.

## Acceptance Criteria

The auth plan is ready to move from design to implementation when:

- gBASIC can read service configuration through `env(name)`,
- gBASIC can generate secure random tokens through `secure_token(length)`,
- password hashing has a safe standard helper,
- WebServer apps can read request cookies,
- response records can set cookies,
- integration tests cover login, logout, CSRF failures, expired sessions, and
  moderation attribution.
